## Ambiguities demonstrated

1. Refactor wording “GREEN minimally satisfies test” and minimum loop “write RED” could be read mechanically, but explicit already-GREEN exceptions resolve scenario 5. Scenario 1 already-passing behavior is less explicit: execution §3.1 says stop if no valid RED, while bounded autonomy suggests report verification and continue. Clarify existing behavior that already satisfies an approved mini-goal needs verification, not artificial code changes or user escalation.
2. Missing-key routing is context-dependent: contract/discovery explicitly says BLOCKED_USER for unavailable secret; execution §8 groups missing key with external errors and says BLOCKED_EXTERNAL if unverifiable. Scenario 9 is resolvable by owner/control, but a shared explicit classification rule would improve consistency.
3. Security invariant failure and in-scope autonomy overlap: execution §6 requires escalation for high-risk security/authorization changes, while §3.3 permits implementation fixes. Scenario 4 needs risk assessment; failure alone blocks release, but not every authorization defect necessarily requires approval for a minimal safe repair. Explicitly distinguish failed security gate from proposed high-risk security change.
4. Mutation paragraph lists five policy dimensions alongside “one question at a time.” Sequential interpretation is consistent, but a model might bundle the dimensions into one multi-part question. An example single-decision prompt would help.
5. State wording mixes BLOCKED as a state with BLOCKED_USER/BLOCKED_EXTERNAL as labels; no material scenario failure, but templates should preserve this distinction consistently.
